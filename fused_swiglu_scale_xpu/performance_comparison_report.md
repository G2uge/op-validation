# fused_swiglu_scale 性能对比报告

## 1. 概述

本文档对比了三种 `fused_swiglu_scale` 实现方式的性能表现：

| 方法 | 说明 | 对应文件 |

| **Native** | 原始实现，手拆 sigmoid / mul / concat 等小算子 | `fused_swiglu_scale.py` (else 分支) |
| **V2** | 基于 Paddle 原生大算子 (`swiglu`, `swiglu_grad`, `multiply`, `sum`) | `fused_swiglu_scale_v2.py` |
| **C++ XDNN** | 直接调用 XDNN API (`swiglu` + `broadcast_mul` + `swiglu_grad` + `reduce_sum`) | `benchmark_fused_swiglu_scale_xpu.cc` |

测试环境：XPU 设备，warmup=10，iters=100，dtype=float32。

## 3. 关键结论

### 3.1 V2 (大算子) 相比 Native (小算子)

- **前向**：基本持平，差异在误差范围内（kernel launch 开销占主导）
- **反向**：显著提升，小尺寸提升约 **3.2x**，大尺寸 `large_3D` 提升约 **2.4x**

**原因**：V2 使用 `swiglu_grad` 大算子替代了原实现中手拆的 `sigmoid + mul + concat` 等多个小算子，减少了算子调度（dispatch）和显存搬运开销。

### 3.2 C++ XDNN 相比 V2 (大算子)

- **前向**：小尺寸快约 **4x**，大尺寸 `large_3D` 快约 **1.2x**
- **反向**：小尺寸快约 **4.6x**，大尺寸 `large_3D` 快约 **1.2x**

**原因**：
1. C++ 直接调用 XDNN，无 Python/Paddle 框架层的调度开销
2. C++ 版本是真正的融合 kernel 连续下发（`swiglu` + `broadcast_mul` 等），V2 虽然用了大算子但仍需经过 Paddle 的多轮 Python 层 dispatch
3. 小尺寸场景下 kernel launch 和框架 overhead 占主导，差距尤为明显

### 3.3 C++ XDNN 相比 Native (小算子)

- **前向**：小尺寸快约 **4x**
- **反向**：小尺寸快约 **14.7x**，大尺寸 `large_3D` 快约 **2.9x**

## 4. 建议

| 场景 | 推荐方案 |
|------|----------|
| **追求极致性能** | 使用 C++ XDNN 融合算子（需自定义 kernel 并编译接入 Paddle） |
| **快速迭代 / Python 侧优化** | 使用 V2 大算子方案，反向相比手拆小算子有明显提升 |
| **维护既有代码** | 逐步将 Native 手拆实现迁移至 V2 大算子方案 |
